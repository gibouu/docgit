## high: Branch and restore overwrites continue after the safety snapshot fails

id: fnd_sig-feat-library-3dc429a783-a38b_8165198832
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Node source apps/desktop/src/main (feat_library_3dc429a783)

evidence:
- apps/desktop/src/main/service.ts:639-653 (DocumentService.commitPath)
- apps/desktop/src/main/service.ts:677-680 (DocumentService.snapshotDiskBeforeOverwrite)
- apps/desktop/src/main/service.ts:442-447 (DocumentService.switchBranch)

The pre-overwrite safety snapshot is best-effort: unreadable or unparseable current disk content returns undefined, and snapshotDiskBeforeOverwrite ignores that result. Branch switch, branch creation, and restore then overwrite the document anyway. If Word or cloud sync leaves the file temporarily unreadable/partial, DocGit can replace the only current on-disk bytes without capturing them first, defeating the stated safety snapshot behavior.

recommendation:
Make snapshotDiskBeforeOverwrite return a success/failure result and abort destructive overwrites when the current file cannot be captured. If preserving unparseable bytes matters, copy the raw file to a rescue file before refusing the branch/restore operation.

test analysis:
The smoke test covers the happy safety-snapshot path with parseable unversioned content, but it never exercises unreadable or unparseable content before a branch switch or restore.

suggested regression test:
In the desktop smoke or a focused service test, create a branch, write invalid bytes to the tracked file, call switchBranch, and assert the operation throws or preserves a raw rescue copy instead of overwriting the file.

minimum fix scope:
DocumentService.snapshotDiskBeforeOverwrite and its destructive callers: createBranch, switchBranch, and restoreVersion.

repro:
Track a valid document with two branches, replace the working file with temporarily unparseable bytes, then call switchBranch. commitPath logs a skip, switchBranch still writes the target branch head, and the unparseable bytes are lost.

repro:

## medium: Link refresh marks links updated before the document write succeeds

id: fnd_sig-feat-library-3dc429a783-e700_93bf8d2a8b
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Node source apps/desktop/src/main (feat_library_3dc429a783)

evidence:
- apps/desktop/src/main/service.ts:581-587 (DocumentService.refreshLinks)
- apps/desktop/src/main/service.ts:590-593 (DocumentService.refreshLinks)

refreshLinks persists lastValue and lastSourceCommitId inside the loop before writing the modified Word document and before committing the resulting version. If writeFileSync throws, or the later commit is skipped, the registry says the link has pulled the new source value while the document still contains the old value. Later refreshes compare against the already-updated lastValue and can skip the repair indefinitely.

recommendation:
Stage link metadata updates until after the file write and version commit succeed. Prefer a transaction or explicit rollback around link row updates, and only advance lastValue/lastSourceCommitId for links whose document update was durably written.

test analysis:
The smoke test verifies successful link propagation, but it does not simulate write failure or commit failure during refreshLinks.

suggested regression test:
Create a linked document, change the source, force the target write or commit to fail, then assert the link remains stale and lastValue still reflects the value actually present in the document.

minimum fix scope:
DocumentService.refreshLinks ordering around updateLinkValue, writeFileSync, and commitPath.

repro:
Make a linked target document unwritable, change the source workbook, and call refreshLinks. The write throws after updateLinkValue has persisted the new value/source commit, leaving links() non-stale even though the target file was not updated.

## medium: Recipient detail requests can show sends for the wrong recipient

id: fnd_sig-feat-library-6238ecca25-61f4_5eaf4c7686
category: concurrency
confidence: high
triage: confirmed-bug
status: open
feature: Node source apps/desktop/src/renderer (feat_library_6238ecca25)

evidence:
- apps/desktop/src/renderer/src/views/SentHistory.tsx:17-20 (SentHistory)
- apps/desktop/src/renderer/src/views/SentHistory.tsx:58-76 (SentHistory)

sends is a single global list rendered under whichever recipient is currently open. When switching from recipient A to B, A's sends remain visible under B until B's request resolves. If A's slower request resolves after B is selected, it can overwrite B's sends indefinitely until another interaction.

recommendation:
Clear sends when open changes and ignore stale responses. For example, capture the requested recipient in the effect, use an alive flag/request id, and only setSends if the request still matches the current open recipient. Alternatively store sends keyed by recipient.

test analysis:
No linked renderer tests cover async recipient switching; the package test script does not execute UI tests.

suggested regression test:
Render SentHistory with deferred sendsToRecipient promises, switch from A to B before A resolves, resolve A last, and assert B never displays A's sends.

minimum fix scope:
apps/desktop/src/renderer/src/views/SentHistory.tsx effect and sends state model.

repro:
With two recipients that each have sends, open recipient A and wait for its sends to load. Then open recipient B. B's expanded row initially renders A's sends; with delayed IPC responses, a stale A response can also overwrite B after B has loaded.

## medium: Tracked move deletions are included in the final Word text

id: fnd_sig-feat-library-2addefc088-2742_cb3b80a531
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Node source packages/core/src/adapters (feat_library_2addefc088)

evidence:
- packages/core/src/adapters/word/parse.ts:10-13
- packages/core/src/adapters/word/parse.ts:125-142 (collectRunText)
- packages/core/test/parse.test.ts:46-55

Word represents tracked moves with w:moveFrom for the old location and w:moveTo for the new location. The adapter promises final-state parsing and skips w:del/w:delText, but all other containers recurse, so w:moveFrom text is retained instead of being treated like deleted text. Documents with pending tracked moves will show duplicated or stale text in DocGit diffs.

recommendation:
Treat w:moveFrom and w:moveFromRangeStart/w:moveFromRangeEnd subtrees as deleted content, while continuing to recurse into w:moveTo like w:ins.

test analysis:
The tracked-change test only covers w:del and w:ins, so the default recursion path for w:moveFrom is never exercised.

suggested regression test:
Add a parseDocx test with w:moveFrom and w:moveTo in one paragraph and assert only the moved-to text remains.

minimum fix scope:
Update collectRunText in the Word adapter and add a focused tracked-move fixture.

repro:
Create a docx paragraph containing <w:moveFrom><w:r><w:t>old place</w:t></w:r></w:moveFrom><w:moveTo><w:r><w:t>new place</w:t></w:r></w:moveTo>. parseDocx currently includes both strings; final-state text should include only the moveTo content.

## medium: Database restore overwrites the live database non-atomically after disposing the service

id: fnd_sig-feat-library-3dc429a783-a78d_e1dcd3ff67
category: data-loss
confidence: medium
triage: risk
status: open
feature: Node source apps/desktop/src/main (feat_library_3dc429a783)

evidence:
- apps/desktop/src/main/backup.ts:31-34 (restoreDatabase)
- apps/desktop/src/main/index.ts:204-210 (backup:restore IPC handler)

restoreDatabase copies directly over docgit.db. If the destination copy fails partway, the main database path can be left truncated or otherwise invalid, and the IPC handler has already disposed the live service before attempting the copy. The exception path does not reopen the store or force a relaunch, so the running app can be left with disposed handlers and a damaged database file despite having validated the backup first.

recommendation:
Restore via a temp file in the same directory: copy the backup to temp, validate/open the temp, then atomically rename it over docgit.db only after the copy completes. If restore fails after disposing the service, relaunch/reopen the original store or exit with a clear recovery path using docgit.db.bak.

test analysis:
The smoke test covers only a successful backup/restore round trip and invalid source validation; it does not simulate copy failure after service disposal or partial destination writes.

suggested regression test:
Inject a failing copy/rename path for restoreDatabase and assert the original dbPath remains valid and the service is not left disposed in a recoverable IPC error path.

minimum fix scope:
restoreDatabase plus the backup:restore IPC handler's failure path.

repro:
Trigger backup restore while the destination copy fails, for example by making the data directory unwritable after validation or exhausting disk space during copy. The service is already closed and docgit.db may be partially overwritten.
