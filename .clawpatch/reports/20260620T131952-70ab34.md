## high: Branch and restore overwrites continue after the safety snapshot fails

id: fnd_sig-feat-library-3dc429a783-a38b_8165198832
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Node source apps/desktop/src/main (feat_library_3dc429a783)

evidence:
- apps/desktop/src/main/service.ts:639-653 (DocumentService.commitPath)
- apps/desktop/src/main/service.ts:677-680 (DocumentService.snapshotDiskBeforeOverwrite)
- apps/desktop/src/main/service.ts:442-447 (DocumentService.switchBranch)

The pre-overwrite safety snapshot is best-effort: unreadable or unparseable current disk content returns undefined, and snapshotDiskBeforeOverwrite ignores that result. Branch switch, branch creation, and restore then overwrite the document anyway. If Word or cloud sync leaves the file temporarily unreadable/partial, DocGit can replace the only current on-disk bytes without capturing them first, defeating the stated safety snapshot behavior.

recommendation:
Make snapshotDiskBeforeOverwrite return a success/failure result and abort destructive overwrites when the current file cannot be captured. If preserving unparseable bytes matters, copy the raw file to a rescue file before refusing the branch/restore operation.

test analysis:
The smoke test covers the happy safety-snapshot path with parseable unversioned content, but it never exercises unreadable or unparseable content before a branch switch or restore.

suggested regression test:
In the desktop smoke or a focused service test, create a branch, write invalid bytes to the tracked file, call switchBranch, and assert the operation throws or preserves a raw rescue copy instead of overwriting the file.

minimum fix scope:
DocumentService.snapshotDiskBeforeOverwrite and its destructive callers: createBranch, switchBranch, and restoreVersion.

repro:
Track a valid document with two branches, replace the working file with temporarily unparseable bytes, then call switchBranch. commitPath logs a skip, switchBranch still writes the target branch head, and the unparseable bytes are lost.

## high: Malformed Excel and PowerPoint packages can become valid-looking empty or mis-mapped models

id: fnd_sig-feat-library-dc9fec9152-32f0_423ff747b7
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Core Document Parsing Adapters (feat_library_dc9fec9152)

evidence:

- packages/core/src/adapters/excel/parse.ts:127-131 (parseWorksheet)
- packages/core/src/adapters/powerpoint/parse.ts:77-89 (parsePptx)
- packages/core/src/adapters/powerpoint/parse.ts:112-115 (parseSlide)
- docs/SPEC.md:49-51

The Excel and PowerPoint adapters do not fail when required OOXML relationships, parts, or roots are missing. A corrupt or malformed Office file can therefore be snapshotted as if whole sheets, slides, or shapes were deleted, or as if a sheet/slide id pointed at the wrong part, which undermines trustworthy diffs and can corrupt DocGit history.

test analysis:

suggested regression test:
Create .xlsx and .pptx fixtures whose workbook/presentation lists an r:id that is absent from the rels file, and fixtures whose rel target points to a missing part; assert parseXlsx/parsePptx throw instead of returning a model with skipped or fallback content. Add malformed worksheet and presentation-root cases as well.

minimum fix scope:
Tighten relationship resolution and required-node validation in packages/core/src/adapters/excel/parse.ts and packages/core/src/adapters/powerpoint/parse.ts, with regression tests in excel.test.ts and powerpoint.test.ts.

## high: Model-only no-op drops media-only document changes

id: fnd_sig-feat-library-641ef069a0-1a0c_85f59f0d4e
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Core Store And Branching (feat_library_641ef069a0)

evidence:
- packages/core/src/store/store.ts:433-441 (SnapshotStore.commit)
- packages/core/src/model/types.ts:48-62 (PresentationModel)
- docs/superpowers/specs/2026-06-16-storage-growth-design.md:12-20

The store decides that a save is a no-op before hashing or comparing file bytes. The normalized models intentionally omit user-visible binary content such as embedded images, so a user can change a picture in a document/deck while the parsed model stays identical. That second save is silently discarded, leaving restore/export/branch switching unable to recover that file state.

recommendation:
Do not use modelHash alone as the persistence no-op boundary. Either include hashes for user-visible non-text parts in DocModel, or compare/store fileHash as well and only treat a save as unchanged when both the semantic model and relevant file content are unchanged.

test analysis:
store.test.ts only checks the no-op path with generated documents whose parsed model and bytes are effectively the same scenario; it does not create two different files that parse to the same model.

suggested regression test:
Add a core test that commits two OOXML byte arrays with the same parsed text model but different media/part bytes, then asserts the second commit is created and getFileBytes returns the newer bytes.

minimum fix scope:
SnapshotStore.commit no-op/coalesce criteria plus model/adapters or a normalized file-content hash for visible non-text OOXML parts.

repro:
Commit an OOXML file with some text and an embedded image, then commit the same extracted text with only the image bytes changed. parseDocument/parsePptx produces the same DocModel, so SnapshotStore.commit returns created:false and the old file bytes remain the branch head.
